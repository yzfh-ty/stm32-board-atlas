# 制作流程与设备迁移

适用项目：[stm32-board-atlas](https://github.com/yzfh-ty/stm32-board-atlas)。
整理日期：2026-10-28。以下“已验证”指原设备上的制作和检查记录，不代表已在新设备上执行过安装。

## 1. 先确定迁移范围

| 目的 | 新设备需要什么 | 是否需要额外带走本机文件 |
| --- | --- | --- |
| 浏览已部署的网站 | 支持 WebGL 的浏览器 | 不需要 |
| 运行、修改、构建网页 | Git、Node.js 22.12+、npm | 不需要，克隆仓库即可 |
| 手动编辑现有三维模型 | 上述环境 + Blender 5.2 | 仓库已包含可编辑的 .blend |
| 继续让 Codex 操作 Blender | 上述环境 + Codex、Python、Blender MCP、技能 | 需要恢复技能和 MCP 配置 |
| 重现最初的程序化建模过程 | 上述完整环境 + 本机原始建模脚本 | 需要额外复制未提交的制作脚本 |

**最省事的迁移方式是先克隆仓库并运行网页，再按需补建模工具。网页运行不依赖 Blender、Codex 或 MCP。**

## 2. 整体制作链路

```mermaid
flowchart LR
    A[确定外形与交互目标] --> B[Codex 读取建模技能]
    B --> C[通过 Blender MCP 执行 bpy]
    C --> D[Blender 建模与材质]
    D --> E[网格检查与多角度查看]
    E --> F[保存 blend 并导出 GLB]
    F --> G[保留或恢复元件分组]
    G --> H[React 与 Three.js 网页]
    H --> I[浏览器检查与构建]
    I --> J[GitHub 与静态部署]
```

各部分的分工：

- **技能（Skills）**：提供建模、材质、导出、质量检查和 Three.js 开发的工作方法。
- **MCP**：连接 Codex 与正在运行的 Blender，提供执行代码、读取场景和查看画面的工具。
- **Blender**：实际生成几何体、材质、文字、灯光和相机。
- **GLB**：把三维模型交给浏览器加载。
- **React / Three.js**：实现界面、模型显示和交互。
- **GitHub / 静态托管**：保存项目并发布网页。

技能存在、MCP 工具已加载、Blender 插件已运行，是不同的检查项；只安装技能不能直接操作 Blender。

## 3. 本次实际制作步骤

### 3.1 准备环境

原设备使用：

| 项目 | 本次制作环境 |
| --- | --- |
| Blender | 5.2.2 LTS |
| Blender MCP 服务包 | mcp-for-blender 2.2.2 |
| 项目 Python 环境 | 3.12.14 |
| 项目技能 | 13 个 Blender 技能、9 个 Three.js 技能 |
| 网页依赖 | 由 package.json 与 package-lock.json 固定 |
| Node.js 要求 | 22.12+；也支持 package.json 声明的 20.19+ |

技能放在项目的 `.agents/skills/`，MCP 配置放在 `.codex/config.toml`。
Codex 的项目技能发现位置与项目级 MCP 配置范围，分别见 [OpenAI 官方技能文档](https://learn.chatgpt.com/docs/build-skills)和 [MCP 文档](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)。

### 3.2 明确板子外观

采用常见蓝色最小系统板的展示形式，板体尺寸为 52 × 23 × 1.6 mm。

建模内容包括 MCU、48 根引脚、USB、稳压器、双晶振、BOOT 跳线、复位按键、排针、SWD、LED、阻容器件、焊盘、丝印和示意走线。

MCU 外形参考 [ST 数据手册](https://www.st.com/resource/en/datasheet/stm32f103c8.pdf)；整板布局是外观设计，不是经电气验证的可生产 PCB。

### 3.3 通过 Blender 建模

- 先查询 Blender 版本和当前场景，确认连接成功。
- 新建专门的场景与模型集合，保留原有场景。
- 使用 bpy 和基础几何体生成各元件。
- 添加塑料、蓝色阻焊、金属、镀金、陶瓷等材质，以及型号、位号与引脚丝印。
- 按真实尺寸建模，保存时保留各元件，便于以后修改。

本机制作脚本为 `tools/blender/create_stm32_minimum.py`，但该文件**未纳入 Git**。只克隆仓库仍可编辑已保存的源模型。

### 3.4 检查并保存资产

检查内容包括：重叠表面、悬空部件、法线、退化面、变换、实际尺寸，以及多角度实体和线框画面。

本次修正了部分焊盘重叠、弯脚接缝与跳帽网格。平面刚性多边形、焊盘与板体的内部接触面按用途保留；恒定颜色材质没有依赖纹理 UV。

产物：

- `models/stm32f103c8t6/stm32f103c8t6.blend`：可编辑源模型。
- 同目录的 `stm32f103c8t6.glb`：按材质合并的静态 GLB。
- `stm32f103c8t6_hero.png`、`stm32f103c8t6_top.png`：展示图。
- `tools/blender/verify_stm32_glb.py`：检查原始 GLB 的格式、索引、法线与尺寸。

GLB 使用米为单位、Y 轴向上。板体尺寸与整模型外接尺寸不同，因为接口和排针会超出板边。

### 3.5 把模型转换成可交互结构

最初的 GLB 按材质合并，适合整体显示，却不能直接按元件选择。

因此使用 `tools/blender/prepare_web_model.py`，根据连续几何块和当前板子的已知布局，恢复元件分组。最终输出：

- `public/models/stm32-interactive.glb`
- `public/models/model-manifest.json`

当前交互模型约 3.85 MB，含 31 个逻辑元件、76 个材质网格、71,860 个三角面。

**这个脚本只适用于当前模型，不是通用的电路板识别程序。** 它带有当前三角面数量和元件数量的断言；模型变化后需要同步调整规则与校验。

以后制作新模型，优先从 Blender 导出时就保留稳定的元件名称与层级，例如 `part_mcu`、`part_usb`、`part_reset`；在同一元件内部按材质合并，避免跨元件合并后丢失选择信息。

### 3.6 制作 Web 展示

参考 Human Atlas 的“全屏模型 + 浮动控制面板”交互形式，使用自己的电路板资产。

| 文件 | 主要职责 |
| --- | --- |
| src/App.tsx | 搜索、分类、详情、滑块与交互状态 |
| src/BoardViewer.tsx | 加载模型、高亮、相机、标注与展开动画 |
| src/board-data.ts | 元件 ID、分类、名称与说明 |
| src/atlas.css | 视觉样式与响应式布局 |

交互功能包括旋转缩放、31 个元件点击和搜索、7 类系统显隐、单独查看、聚焦、5 种预设视角、自动旋转及爆炸展开。

模型节点 ID 与说明数据必须对应。原设备检查过直接点击、搜索、分类隐藏、单独查看、俯视、展开和页面刷新；这不等于所有设备与浏览器均已验证。

### 3.7 构建与发布

```bash
npm run check
npm run build
```

正式部署上传整个 `dist/`，不要只上传 HTML。

项目配置了相对资源路径 `base: './'`，模型地址使用 `BASE_URL`。原设备曾验证根目录与仓库子目录下的资源访问。

源码已推送到 GitHub。Vercel 配置与 GitHub Pages 手动工作流已在仓库中，具体部署见 [README](../README.md#部署)。提交信息使用英文。

## 4. 迁移方式 A：只运行或修改网页

在新设备安装 Git、Node.js 和 npm，然后执行：

```bash
git clone https://github.com/yzfh-ty/stm32-board-atlas.git
cd stm32-board-atlas
npm ci
npm run dev
```

打开 `http://127.0.0.1:5173/`。

验证构建：

```bash
npm run build
npm run preview
```

打开 `http://127.0.0.1:4173/`。这是本地构建预览，不是生产服务器。

无需复制 `node_modules/`、`dist/`、`.cache/` 或 `.tools/`，也无需安装 Python、Blender 和 MCP。

## 5. 迁移方式 B：恢复完整建模工作环境

### 5.1 从原设备额外带走哪些文件

除了克隆仓库，额外备份：

| 路径 | 用途 |
| --- | --- |
| .agents/skills/ | 22 个项目技能，须连同 scripts、references 等内容完整复制 |
| tools/blender/create_stm32_minimum.py | 最初的程序化建模脚本 |
| tools/blender/export_stm32_asset.py | 原制作流程的静态导出与出图脚本 |
| tools/blender/export_stm32_web.py | 按源场景逻辑对象分组的另一条导出路径，迁移时需重新验证 |
| tools/blender/qa_stm32_asset.py | 适配本模型尺寸的检查脚本 |
| tools/blender/requirements.lock.txt | 原 Windows Python 环境依赖记录 |
| tools/blender/start-blender.ps1 | 本机启动脚本，需改 Blender 路径 |
| tools/blender/enable-addon.py | 原插件启用辅助脚本，可选 |
| tools/blender/verify-mcp.py | 原 MCP 联通检查脚本，需改插件路径 |
| .codex/config.toml | 作为配置模板，不能原样照搬绝对路径 |

这些内容目前被 Git 忽略，**git clone 不会带下来**。不要复制整个账号配置目录；项目配置与技能足够作为恢复起点。

`prepare_web_model.py`、`verify_stm32_glb.py` 已在仓库中，不需要额外备份。

### 5.2 重建 Python 环境

不复制旧的 `.venv`。它包含操作系统和安装路径相关内容，应在新机器重建。

Windows PowerShell，先进入新项目根目录：

```powershell
py -3.12 -m venv .tools\blender-mcp\.venv
.\.tools\blender-mcp\.venv\Scripts\python.exe -m pip install "mcp-for-blender==2.2.2"
```

这是按原服务版本恢复的建议步骤，未在新设备实际执行。若需要完整复现原 Windows 依赖，可在已复制锁文件、确认 Python 版本匹配后改用：

```powershell
.\.tools\blender-mcp\.venv\Scripts\python.exe -m pip install -r tools\blender\requirements.lock.txt
```

锁文件含 Windows 专用依赖，不要原样用于 macOS/Linux。macOS/Linux 可用 Python 3 创建项目虚拟环境并安装同一服务包；可执行文件位于 `.venv/bin/`，而非 `.venv/Scripts/`。

### 5.3 安装并启用 Blender 端插件

安装 Blender 5.2；先打开一次，以建立新用户的配置目录。

Windows 示例：

```powershell
$addonDir = Join-Path $env:APPDATA 'Blender Foundation\Blender\5.2\scripts\addons'
.\.tools\blender-mcp\.venv\Scripts\mcp-for-blender.exe install-addon --addons-dir $addonDir
```

随后在 Blender 的 **Edit → Preferences → Add-ons** 中启用 **MCP for Blender**。
在三维视图按 **N**，查看 MCP 面板；如果服务未运行，点击 **Start MCP Server**。参见 [Blender MCP 项目说明](https://github.com/ahujasid/mcp-for-blender#installing-the-blender-addon)。

使用新设备实际安装的用户配置路径。只让一个 Blender 实例占用同一个 9876 端口。

### 5.4 恢复项目技能与 MCP 配置

把备份中的完整技能目录放回新项目的 `.agents/skills/`。项目中应有 13 个 `blender-*` 和 9 个 `threejs-*` 目录，各自包含 `SKILL.md`。

项目级 MCP 配置需要新项目处于受信任状态才会加载；技能变化通常会被检测，未显示时重新加载项目或重启客户端。依据：[OpenAI 官方技能发现说明](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills)、[项目 MCP 配置说明](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)。

以下示例假设新项目位于 `D:\work\stm32-board-atlas`。请先替换为真实路径，再写入 `.codex/config.toml`：

```toml
[mcp_servers.blender]
command = 'D:\work\stm32-board-atlas\.tools\blender-mcp\.venv\Scripts\mcp-for-blender.exe'
args = []
cwd = 'D:\work\stm32-board-atlas'
enabled = true
startup_timeout_sec = 30
tool_timeout_sec = 120
enabled_tools = ['get_addon_status', 'get_scene_info', 'execute_blender_code', 'look', 'disable_telemetry']

[mcp_servers.blender.env]
BLENDER_HOST = '127.0.0.1'
BLENDER_PORT = '9876'
BLENDER_MCP_DISABLE_TELEMETRY = '1'
BLENDER_MCP_SAFE_MODE = '1'
PYTHONUTF8 = '1'
```

不要把旧机器的 `E:\project\3dweb`、Blender 安装盘符或用户目录直接搬入新配置。若沿用旧配置里的 `APPDATA`、`TEMP`、`TMP`、`BLENDERMCP_ADDONS_DIR`，也需改成新机器实际路径，并确保缓存目录已存在。

### 5.5 修改原制作脚本中的路径

在编辑器中搜索旧项目路径、旧 Blender 安装路径和旧 Windows 用户目录，重点检查：

- `create_stm32_minimum.py` 的输出目录。
- `export_stm32_asset.py` 的模型、截图与保存路径。
- `export_stm32_web.py` 的项目根目录。
- `start-blender.ps1` 的 Blender 可执行文件路径。
- `verify-mcp.py` 的 Blender 插件目录与缓存设置。

仓库内的 `prepare_web_model.py` 和 `verify_stm32_glb.py` 已通过脚本所在位置定位项目根目录，不依赖原设备的盘符。

在新设备首次继续工作时，先打开现有 `.blend`，从查看与小修改开始；不要直接反复运行最初的整板创建脚本。原创建脚本不是保证可重复执行的更新器，可能生成额外场景或重名对象。

### 5.6 验证完整链路

依次确认：

1. Codex 能看到项目技能。
2. MCP 能返回 `get_addon_status`，并报告连接到 Blender。
3. `get_scene_info` 能读到当前源模型。
4. `execute_blender_code` 能运行简单的 bpy 查询。
5. `look` 能返回实际画面。
6. 模型导出后，网页能加载、选择和展开元件。

可在新对话中直接要求：

> 先只读检查项目技能与 Blender MCP。依次查询插件状态、场景信息、Blender 版本，并获取一张模型预览；确认全部成功后再修改模型。

本机启用了 MCP 安全模式。原制作中曾遇到外部脚本导入、sys、lambda 和文本数据块等操作受限，后续改写为允许的 bpy/bmesh 代码。迁移后仍应保留安全设置，在允许范围内改写；完整脚本可以在你控制的 Blender 脚本环境中运行。

端口监听正常，只说明桥接服务有响应条件，不能代替上述实际工具调用验证。

## 6. 后续更新时的固定顺序

1. 保存一份可编辑的 `.blend`。
2. 修改几何体或材质。
3. 检查尺寸、网格与多角度外观。
4. 导出 GLB，保持元件名称、层级、米制单位和轴向一致。
5. 如仍沿用当前恢复分组方案，运行：

   ```bash
   python tools/blender/prepare_web_model.py
   ```

6. 如导出结构或元件 ID 改变，同步更新 `src/BoardViewer.tsx` 和 `src/board-data.ts`。
7. 检查选择、分类、单独查看、展开、视角与页面刷新。
8. 运行 `npm run build`，再通过 HTTP 预览。
9. 使用英文提交信息提交并推送，按所选平台重新部署。

GitHub Pages 的现有工作流是**手动触发**：推送后仍需按 README 运行工作流。

## 8. 迁移完成的判定

- 网页迁移：新设备可克隆、安装、启动，模型出现且基本交互正常。
- 建模迁移：还需能打开源模型、修改并保存，再导出给网页使用。
- AI 建模迁移：还需技能可发现、MCP 实际工具调用和截图成功。
- 发布迁移：新设备重新完成 GitHub 身份验证，推送后核对远程分支；部署成功以平台结果及实际访问为准。

复制项目目录或延续聊天记录，不会自动安装工具、重建环境或迁移账号登录状态。
